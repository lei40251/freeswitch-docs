# 第 43 章：解读 SIP 跟踪与 CDR {#chapter-43-reading-a-sip-trace-and-a-cdr}

呼叫行为异常时，两类资料几乎可以提供全部所需信息：**SIP 跟踪**记录建立和拆除呼叫的信令，**CDR**（呼叫详单）在呼叫结束时写入。跟踪显示*两个端点交换了什么*，CDR 显示*呼叫如何结束、各阶段持续多久*。结合阅读即可将故障定位到特定呼叫腿和时刻。

本章是诊断指南，不是协议教程。内容包括启用 `mod_sofia` 跟踪、观察正常 SIP 事务和常见异常、读取 `mod_cdr_csv` 行，以及通过 `Call-ID` 和 UUID 关联两类资料。

## 捕获 {#capture}

SIP 跟踪由 Sofia 协议栈提供，通过控制台 `sofia` API 启用。控制方式从粗到细分为三类。

**一次跟踪全部配置实例：**

```
sofia global siptrace on
```

**跟踪单个配置实例：** 将 `<profile>` 替换为 `internal` 或 `external` 等实例名：

```
sofia profile <profile> siptrace on
```

使用 `off` 关闭任一方式。通常应按实例跟踪，只输出承载待查呼叫的实例流量，使日志更易读。

若需观察 Sofia-SIP 传输层和事务层的更多细节，例如报文看似发出却始终未确认，可提高 sofia-sip 库日志级别：

```
sofia loglevel all 9
```

`loglevel` 接受组件和 `0`（静默）到 `9`（最详细）的级别。有效组件为 `all`、`default`、`tport`、`iptsec`、`nea`、`nta`、`nth_client`、`nth_server`、`nua`、`soa`、`sresolv` 和 `stun`。`all` 一次设置全部组件，也可指定单个组件，例如 `sofia loglevel tport 9` 查看传输细节。另一个相关命令 `sofia tracelevel <level>` 设置跟踪行使用的 FreeSWITCH 日志级别。

:::tip
跟踪输出很多。复现前启用，捕获呼叫后立即用 `sofia profile <profile> siptrace off` 关闭。vanilla 配置将 `internal` 的跟踪开关绑定到控制台 F10/F11。
:::

跟踪与其他信息一起出现在 **FreeSWITCH 日志**中，因此应过滤。`fs_cli` 中使用 `/log info` 或更高详细程度，确保显示相关行；可将控制台保存到文件，或读取 `log/freeswitch.log`，事后搜索呼叫。每条跟踪消息先显示方向，即*发往*或*收自*某对端地址，随后是完整 SIP 报文。首先读取方向，判断消息是 FreeSWITCH 发起还是仅由其接收。

## 解读跟踪 {#read-the-trace}

### 正常呼叫的基本形态 {#the-shape-of-a-normal-call}

成功呼叫是一小段可预测的消息序列。解读主要是确认序列是否发生，若未完成则找到停止的位置。正常已应答呼叫如下：

```
  caller (or upstream)            FreeSWITCH
        |  INVITE  ----------------->  |   request: caller wants to set up a call
        |  <----------------  100 Trying    provisional: request received, working on it
        |  <----------------  180 Ringing   provisional: remote end is alerting
        |  <----------------  200 OK         final: call answered, SDP for media included
        |  ACK  ------------------->  |   caller confirms the 200 OK; media flows
        |            ... talk ...        |
        |  BYE  ------------------->  |   either side hangs up
        |  <----------------  200 OK         confirms the BYE; call torn down
```

从上到下阅读：

- **`INVITE`** 发起呼叫并携带主叫的媒体提议（SDP）。
- **`100 Trying`** 表示收到请求。出站腿没有该响应，可能说明下一跳未收到 INVITE，应检查路由或网络，而非呼叫逻辑。
- **`180 Ringing`** 或 `183 Session Progress` 表示对端正在提示或报告进展。到达 `180` 却没有 `200`，说明振铃后未应答。
- **`200 OK`** 是应答，携带应答方 SDP，此时完成媒体协商。
- **`ACK`** 完成三次握手。`200 OK` 后没有 `ACK` 是典型 NAT 症状：应答发出但未到达发起方。
- **`BYE` / `200 OK`** 表示正常拆除。谁发送 `BYE`，谁就是挂断方。

### 认证：401/407 挑战 {#authentication-the-challenge}

已注册端点或需要认证的中继，首次 INVITE 不会直接接通。FreeSWITCH 发出挑战，端点携带凭据重新发送请求：

```
        |  INVITE (no credentials)  ----------->  |
        |  <-------------  407 Proxy Authentication Required
        |  ACK  ------------------------------>  |   acknowledges the 407
        |  INVITE (with Proxy-Authorization)  -->  |   same request, now signed
        |  <--------------------------  100 Trying / 200 OK
```

这种先挑战再重发的过程是**正常且预期的**，不要将 `401 Unauthorized` 或 `407 Proxy Authentication Required` 本身当作故障。失败是指*第二次* INVITE 仍被拒绝，例如反复 `401`/`407` 或收到 `403 Forbidden`，说明凭据错误或用户未配置。`401` 用于用户代理直接发出的挑战，`407` 用于代理发出的挑战，诊断方法相同。

### re-INVITE {#re-invite}

**re-INVITE** 是*已建立对话内*再次发送的 INVITE：相同 `Call-ID`、相同 `From`/`To` 标签、更大的 `CSeq`。它在通话中重新协商媒体，例如保持、恢复或切换编解码器。音频中途消失时，查找对应时刻附近的 re-INVITE 并读取 SDP，媒体变化常是原因。

### 关键头字段与 SDP 行 {#the-headers-and-sdp-lines-that-matter}

无需逐个阅读所有头字段。运维诊断中，以下四类头字段和三类 SDP 行最有用：

| 字段 | 提供的信息 |
|---|---|
| `Via` | 请求经过的路径。FreeSWITCH 添加的 `received=` / `rport=` 揭示 NAT 后发送者的真实公网地址。 |
| `From` / `To` | 逻辑通信双方。`tag=` 标识对话，消息间匹配的标签可确认属于同一呼叫。 |
| `Contact` | 对端希望接收后续请求的地址。公网入站呼叫中若为 `10.x` / `192.168.x` 等私网地址，表明 NAT 配置错误，后续回复不可路由。 |
| `Call-ID` | 唯一对话标识，用于关联某条腿的全部消息，以及将跟踪与 CDR 关联，见[关联](#correlate)。 |

INVITE 和 `200 OK` 携带的 SDP 正文中，三类行有助于定位媒体问题：

| SDP 行 | 提供的信息 |
|---|---|
| `c=` | **连接地址**，即对端期望接收媒体的 IP。公网呼叫中若指向私网地址，是 NAT 导致单向或无音频的典型特征。 |
| `m=` | **媒体行**：媒体类型、端口和提议的载荷编号列表，例如 `m=audio 16384 RTP/AVP 0 8 101`。端口为 `0` 表示禁用该流。 |
| `a=rtpmap:` | 将载荷编号映射到编解码器名称，例如 `a=rtpmap:0 PCMU/8000`。对比提议与应答的集合，没有共同编解码器则协商失败，属于编解码器不匹配而非网络故障。 |

以下是 INVITE 中可能出现的示例 SDP：

```
v=0
o=FreeSWITCH 1632858000 1632858001 IN IP4 198.51.100.10
s=FreeSWITCH
c=IN IP4 198.51.100.10
t=0 0
m=audio 16384 RTP/AVP 0 8 101
a=rtpmap:0 PCMU/8000
a=rtpmap:8 PCMA/8000
a=rtpmap:101 telephone-event/8000
a=fmtp:101 0-16
a=ptime:20
```

此例表示对端期望在 `198.51.100.10:16384` 接收音频，提供 PCMU（`0`）、PCMA（`8`）和 DTMF 事件（`101`）。若应答 SDP 仅为 `m=audio ... RTP/AVP 9`（G.722），则与 PCMU/PCMA 没有交集，音频协商失败。如果任一 SDP 的 `c=` 为 `10.x` 或 `192.168.x`，而信令经过公网，则可能出现单向或无音频，这是[音频故障](./audio-problems.mdx)章节介绍的典型 NAT 判断方式。

## 解读 CDR {#read-the-cdr}

呼叫结束时，`mod_cdr_csv` 为每条需要记录的呼叫腿写入一行。vanilla 默认只记录 **A 腿**（`<param name="legs" value="a"/>`），并选择 **`example`** 模板（`<param name="default-template" value="example"/>`），所以记录默认写入 `log/cdr-csv/Master.csv`。完整 CDR 后端配置见[第 27 章：呼叫详单](/integration/cdr)。

`example` 模板按以下顺序输出字段：

```
"${caller_id_name}","${caller_id_number}","${destination_number}","${context}","${start_stamp}","${answer_stamp}","${end_stamp}","${duration}","${billsec}","${hangup_cause}","${uuid}","${bleg_uuid}","${accountcode}","${read_codec}","${write_codec}"
```

| 字段 | 含义 |
|---|---|
| `caller_id_name`、`caller_id_number` | 主叫显示名称和号码。 |
| `destination_number` | 拨打号码或请求目标。 |
| `context` | 处理呼叫的拨号计划上下文。 |
| `start_stamp` | 呼叫腿开始时间，即收到 INVITE 或创建通道的时间。 |
| `answer_stamp` | 呼叫应答时间，即 `200 OK`。**从未应答则为空。** |
| `end_stamp` | 呼叫结束或挂断时间。 |
| `duration` | 从 `start_stamp` 到 `end_stamp` 的总秒数。 |
| `billsec` | 从 `answer_stamp` 到 `end_stamp` 的计费秒数，即通话时长。 |
| `hangup_cause` | 呼叫结束原因，见下文。 |
| `uuid` | 此呼叫腿的通道 UUID。 |
| `bleg_uuid` | 若已桥接，表示另一条呼叫腿的 UUID。 |
| `accountcode` | 通道上设置的计费或账户标签。 |
| `read_codec`、`write_codec` | 已协商的入站和出站音频编解码器。 |

### 从单条记录定位故障 {#localizing-a-fault-from-one-line}

结合三个时间戳和 `billsec`，可以判断*呼叫推进到了哪一步*：

- **`answer_stamp` 为空且 `billsec` = `0`：** 呼叫从未接通。主叫拨号后目标未应答，是否振铃需看跟踪中有无 `180`。`hangup_cause` 解释原因，常见为 `NO_ANSWER`、`USER_BUSY`、`CALL_REJECTED` 或 `NO_ROUTE_DESTINATION`。
- **`answer_stamp` 存在但 `billsec` 很小：** 呼叫应答后几乎立即断开，常因媒体失败，例如没有共同编解码器、无音频触发监测机制挂断，或端点因单向音频而挂断。交叉检查 `read_codec`/`write_codec` 和跟踪中的 SDP。
- **`answer_stamp` 存在、`billsec` 合理且 `hangup_cause` = `NORMAL_CLEARING`：** 正常完成的呼叫，无需继续追查。

**`hangup_cause`** 是初步诊断最有用的 CDR 字段。常见值及其指向如下：

| `hangup_cause` | 典型解释 |
|---|---|
| `NORMAL_CLEARING` | 呼叫完成，一方正常挂断。 |
| `USER_BUSY` | 目标忙线。 |
| `NO_ANSWER` | 已振铃但无人应答。 |
| `CALL_REJECTED` | 对端主动拒绝，常见为 `403`/`603`。 |
| `NO_ROUTE_DESTINATION` | 没有匹配的拨号计划路由或下一跳，属于[呼叫建立失败](./call-setup-failures.mdx)章节讨论的路由问题。 |
| `INCOMPATIBLE_DESTINATION` | 协商失败，通常是编解码器不匹配。 |
| `RECOVERY_ON_TIMER_EXPIRE` | 会话或无应答等定时器到期。 |

**`bleg_uuid`** 表示呼叫是否桥接，以及桥接到了哪里。为空表示此腿从未与其他腿桥接，应检查入站侧的路由、认证或发起方；有值则说明到达第二条腿，可查询那条腿自己的记录或通道数据，观察*另一侧*结果。结合 A、B 腿的 `hangup_cause`，可将故障缩小到桥接的一侧。

## 关联 {#correlate}

跟踪与 CDR 从两个角度描述同一呼叫。关联两者，可从一方的症状找到另一方的证据。

**通过 `Call-ID` ↔ UUID。** 一条腿的所有 SIP 消息携带相同 `Call-ID`，对应 CDR 携带通道 `uuid`。FreeSWITCH 不保证 SIP `Call-ID` 与内部 `uuid` *相同*，但会将入站 SIP `Call-ID` 保存在 `sip_call_id` 通道变量中，可据此关联：

1. 在 CDR 中找到失败的腿，例如 `hangup_cause` 为 `INCOMPATIBLE_DESTINATION`、`billsec` 为空的记录，记下其 `uuid`。
2. 跟踪中该呼叫的消息共用同一 `Call-ID`。将 `sip_call_id` 加入 CDR 模板，或在通话仍活动时通过 `uuid_dump <uuid>` 读取，将 `uuid` 映射到 `Call-ID`，从日志提取该腿消息。
3. 结合两者：CDR 的 `hangup_cause` 和时间戳说明*何时出了什么问题*，跟踪中 INVITE/`200 OK` 的 SDP 说明*为什么*，例如 `c=` 地址指向 NAT，或 `a=rtpmap` 交集指向编解码器。

**通过 UUID 跨腿关联。** 桥接呼叫中，A 腿 CDR 的 `bleg_uuid` 就是 B 腿的 `uuid`。这一字段可从一侧记录找到另一侧记录，再找到其 `Call-ID` 和对应跟踪片段，从而确定“失败的呼叫”究竟是哪条腿失败。这是每次故障排查最终都需要回答的问题。
