# 第 47 章：出站事件套接字 {#chapter-47-the-outbound-event-socket}

入站事件套接字（参见 [ESL：入站模式](/programming/esl-inbound)）由应用程序向 FreeSWITCH 主动建立 TCP 连接，认证后控制整个系统。**出站（outbound）事件套接字**则反过来：FreeSWITCH 充当客户端。拨号计划在某路通话上执行 `socket` 应用时，FreeSWITCH 主动建立到你运行的服务器的 TCP 连接，由对端程序控制这一路通话。

这非常适合“每次呼叫建立一条连接”的控制模式。每个执行到 `socket` 动作的呼叫，都会获得一条已经绑定到该通道的独立连接；无需密码，也无需通过 `api uuid_...` 间接定位通道。处理程序可以应答、播放提示音、收集按键、桥接及挂机。呼叫结束后，套接字随之关闭。

## 从拨号计划调用 {#invoking-it-from-the-dialplan}

出站套接字通过 `mod_event_socket` 注册的 `socket` 拨号计划应用启动：

```c
SWITCH_ADD_APP(app_interface, "socket", "Connect to a socket", "Connect to a socket",
               socket_function, "<ip>[:<port>]", SAF_SUPPORT_NOMEDIA);
```

（见 `mod_event_socket.c` 第 1198 行。）可像调用其他拨号计划应用一样使用它：

```xml
<action application="socket" data="127.0.0.1:8084 async full"/>
```

`data` 中第一个空格分隔的字段是目标地址，其余字段为标志。`socket_function` 使用空格拆分 `data`，并把第一个参数视为主机地址（`mod_event_socket.c` 第 430–431 行）。主机字段本身还支持以下形式：

- **`host:port`**：根据最后一个 `:` 拆分端口。未指定时默认端口为 **8084**（第 417 行的 `port = 8084;`，第 451–454 行解析端口）。
- **`host:port/path`**：可以带可选的尾部 `/path`；该路径被剥离并保存到通道变量 `socket_path`，主机名则保存到 `socket_host`（第 456–461 行）。
- **`hostA:port|hostB:port`**：主机字段还可用 `|` 分隔成最多 50 个候选目标。FreeSWITCH 按顺序连接，使用第一个应答的服务器（第 439–484 行）。这样可以在多个处理服务器间实现简单故障转移。

### `async` 与 `full` 标志 {#the-async-and-full-flags}

主机之后的空格分隔字段会以不区分大小写的方式，与 `full` 和 `async` 这两个标志名逐一比较（`mod_event_socket.c` 第 514–520 行）：

```c
for (x = 1; x < argc; x++) {
    if (argv[x] && !strcasecmp(argv[x], "full")) {
        switch_set_flag(listener, LFLAG_FULL);
    } else if (argv[x] && !strcasecmp(argv[x], "async")) {
        switch_set_flag(listener, LFLAG_ASYNC);
    }
}
```

标志顺序无关紧要，任何不是 `full` 或 `async` 的字段都会被忽略。

**`async`** 改变处理程序运行期间 `socket` 应用在 **FreeSWITCH 内部**的执行方式。默认同步模式下，通道会阻塞在 `socket` 应用中，每条命令执行完成后才读取下一条命令。启用 `async` 后，FreeSWITCH 创建独立的监听线程并将通话驻留，使通道在处理程序继续发送命令时，仍可处理事件和已排队的应用命令（第 522–549 行）。换言之，`async` 允许发送 `sendmsg` / `execute`，而不必等待每个操作阻塞读取循环。连接应答会在 `Socket-Mode` 头字段中返回选择的模式：`async` 或 `static`（第 2026 行）。

**`full`** 除每通道命令外，还允许出站连接使用**全局**命令集，包括 `sendevent`、`api`、`bgapi`、日志订阅等。未启用 `full` 时，连接只能操作自身绑定的通道。这项限制在命令解析器中直接实施（`mod_event_socket.c` 第 2225–2227 行）：

```c
if (switch_test_flag(listener, LFLAG_OUTBOUND) && !switch_test_flag(listener, LFLAG_FULL)) {
    goto done;
}
```

在该检查**之前**处理的 `connect`、`getvar`、`myevents`、`sendmsg`、`linger`、`nolinger` 和事件订阅命令，在任何出站连接中都能使用；之后处理的命令必须启用 `full` 才能执行。连接应答会通过 `Control` 头字段报告权限：`full` 或 `single-channel`（第 2027 行）。

:::tip
处理程序需要并行发送命令或访问更广泛的 API 时，使用 `async full`；对于简单的“应答、播放提示音、挂机”流程，直接使用 `socket`（同步、单通道）即可，此时每一步的阻塞执行正是所需行为。
:::

## 连接握手 {#the-handshake}

FreeSWITCH 主动连接处理服务器后，双方仍使用与入站模式相同的基于文本行的事件套接字协议，只有一点不同：**不需要身份认证**。出站连接已经通过认证并绑定到相应通道（第 512–513 行设置 `LFLAG_AUTHED` 和 `LFLAG_OUTBOUND`）。

客户端第一条命令为 `connect`。FreeSWITCH 回应时，会构建包含通道 Caller Profile 及所有变量的 `CHANNEL_DATA` 事件，并序列化后发送（`mod_event_socket.c` 第 2012–2036 行）：

```c
if (!strncasecmp(cmd, "connect", 7)) {
    switch_set_flag_locked(listener, LFLAG_CONNECTED);
    switch_event_create(&call_event, SWITCH_EVENT_CHANNEL_DATA);
    /* ... fills in caller profile + channel variables ... */
    switch_event_add_header_string(call_event, SWITCH_STACK_BOTTOM, "Content-Type", "command/reply");
    switch_event_add_header_string(call_event, SWITCH_STACK_BOTTOM, "Reply-Text", "+OK\n");
    switch_event_add_header_string(call_event, SWITCH_STACK_BOTTOM, "Socket-Mode", /* async | static */);
    switch_event_add_header_string(call_event, SWITCH_STACK_BOTTOM, "Control",     /* full | single-channel */);
    /* serialized and sent back over the socket */
}
```

该应答块是呼叫的即时快照：包含 `Channel-*` 头字段、主叫号码、被叫号码、所有通道变量，以及描述所选标志的 `Socket-Mode`、`Control` 字段。头字段名称会经过规范化，例如 `Channel-Unique-ID` 和 `Caller-Unique-ID`（后续命令需要使用的通道 UUID）。

完成 `connect` 后，出站套接字可使用的每通道命令包括：

| 命令 | 作用 |
| --- | --- |
| `connect` | 绑定呼叫并接收 `CHANNEL_DATA` 应答。 |
| `linger` / `linger <seconds>` | 挂机后保持套接字打开，以便收完剩余事件。未带参数的 `linger` 无限期保持，`linger 5` 保持 5 秒。未指定数字时默认一直保持到断开连接（第 2420–2435 行）。 |
| `nolinger` | 关闭 linger 功能（第 2439–2444 行）。 |
| `myevents` | 只订阅本通道事件（见下文）。 |
| `sendmsg` | 向绑定的呼叫发送消息，主要用于执行应用（第 2169–2223 行）。 |
| `getvar <name>` | 读取单个通道变量（第 2037–2051 行）。 |

### 使用 `myevents` 订阅事件 {#subscribing-with-myevents}

仅执行 `connect` 可以取得呼叫数据，但不会持续接收事件流。若要跟踪呼叫执行过程，需要发送 `myevents`。在出站套接字中，该命令使**本连接**仅订阅**自身绑定通道**的事件，包括应答、执行、执行完成、DTMF、挂机及其他通道事件（`mod_event_socket.c` 第 2052–2124 行）。此后，该通话产生的事件会作为消息送到套接字，供处理程序读取。可以附加 `plain`（默认）、`xml` 或 `json` 作为序列化格式。

### 同步与异步执行 {#sync-vs-async-execution}

处理程序通过在通道上执行拨号计划应用来控制呼叫。在协议层面，使用 `sendmsg`，包含 `call-command: execute` 以及 `execute-app-name` / `execute-app-arg` 头字段。ESL 库会为你构造这样的命令（`libs/esl/src/esl.c`，`esl_execute`，第 530–559 行）：

```c
snprintf(send_buf, sizeof(send_buf), "%s\ncall-command: execute\n%s%s%s%s\n",
         cmd_buf, app_buf, arg_buf,
         handle->event_lock    ? "event-lock: true\n" : "",
         handle->async_execute ? "async: true\n"      : "");
```

由此产生两种执行模式：

- **同步模式**：默认情况下，通道必须完成当前应用，才会读取下一条命令。如果已通过 `myevents` 订阅事件，应用开始时会收到 `CHANNEL_EXECUTE`，结束时会收到 `CHANNEL_EXECUTE_COMPLETE`。通过等待后者，可以确认一次 `playback` 是否真的结束、`play_and_get_digits` 收集了哪些按键等。
- **异步模式**：连接或单条 `sendmsg` 标记为 `async` 时，命令会作为私有事件入队，并立即返回控制权（`mod_event_socket.c` 第 2169–2207 行；第 2172–2177 行处理单条消息的 `async` 头）。这样就能连续排队多个应用，或中断正在执行的应用，而不必等待每条完成。

`event-lock: true` 头字段（由库的 `setEventLock` 设置）可以强制已排队应用严格按发送顺序执行，即使在异步模式下也是如此。这适用于希望异步投递但保持执行顺序的场景。

## 完整示例：出站模式下使用 ESL 库 {#a-worked-example-the-esl-library-in-outbound-mode}

FreeSWITCH 在 `libs/esl` 中提供 Event Socket Library（ESL），并以 `ESLconnection` 和 `ESLevent` 对象 API 封装协议，可供 C++、Lua、Perl、Python、Ruby 等语言使用。出站模式使用一个特别的构造函数，接收服务端 `accept()` 返回的套接字文件描述符（`libs/esl/src/esl_oop.h` 第 81 行；`esl_oop.cpp` 第 45–49 行实现）：

```cpp
ESLconnection::ESLconnection(int socket)
{
    connection_construct_common();
    esl_attach_handle(&handle, (esl_socket_t)socket, NULL);
}
```

`esl_attach_handle` 会自动完成握手：发送 `connect\n\n`，并将收到的 `CHANNEL_DATA` 应答保存为连接的*信息事件*（`libs/esl/src/esl.c` 第 454–492 行）：

```c
esl_send_recv(handle, "connect\n\n");
if (handle->last_sr_event) {
    handle->info_event = handle->last_sr_event;
    /* ... */
}
```

因此构造函数返回时，就已经可以通过 `getInfo()` 获取呼叫数据。典型方式是运行自己的 TCP `accept` 循环，对每个新连接取得文件描述符并构造新的 `ESLconnection`。用于呼叫控制的 ESL 方法（`esl_oop.h` 第 73–101 行）包括：

- `getInfo()`：取得该通话的 `CHANNEL_DATA` 事件。
- `event:getHeader(name)`：读取任意事件的头字段，例如 `unique-id`。
- `execute(app, arg, uuid)`：同步执行拨号计划应用，返回应答事件（`esl_oop.cpp` 第 179–188 行）。
- `executeAsync(app, arg, uuid)`：异步执行应用（第 191–207 行）。
- `recvEvent()` / `recvEventTimed(ms)`：读取下一条通道事件，通常在 `myevents` 后使用（第 232–259 行）。
- `setEventLock(val)` / `setAsyncExecute(val)`：切换上文介绍的头字段（第 163–177 行）。

仓库自带的出站示例 `libs/esl/perl/server.pl` 展示了完整处理流程，也是源码中最简洁且正确的出站处理程序：

```perl
require ESL;
use IO::Socket::INET;

my $sock = IO::Socket::INET->new(LocalHost => "127.0.0.1", LocalPort => 8084,
                                 Proto => 'tcp', Listen => 1, Reuse => 1);
die "Could not create socket: $!\n" unless $sock;

for (;;) {
    my $new_sock = $sock->accept();      # FreeSWITCH connected out to us
    my $pid = fork();
    if ($pid) { close($new_sock); next; } # parent keeps listening

    my $fd  = fileno($new_sock);
    my $con = ESL::ESLconnection->new($fd);   # sends "connect", binds to the call
    my $info = $con->getInfo();               # the CHANNEL_DATA reply
    my $uuid = $info->getHeader("unique-id");

    $con->execute("answer", "", $uuid);
    $con->execute("playback", "/usr/share/freeswitch/sounds/.../ivr-welcome.wav", $uuid);
    $con->execute("hangup", "", $uuid);

    close($new_sock);
    exit;
}
```

下面是同样思路的 Lua 示例，并额外使用 `myevents`，以便收集按键并从 `CHANNEL_EXECUTE_COMPLETE` 事件读取 `play_and_get_digits` 的结果。Lua 绑定提供与 `esl_oop.h` 相同的方法名，并通过 `ESL.ESLconnection(fd)` 构造对象：

```lua
require("ESL")

-- 'fd' is the file descriptor of a socket your accept loop just accepted.
local con  = ESL.ESLconnection(fd)        -- handshake: sends "connect"
local info = con:getInfo()                -- CHANNEL_DATA reply
local uuid = info:getHeader("unique-id")

con:execute("answer", "", uuid)
con:execute("playback", "ivr/ivr-welcome.wav", uuid)

-- Subscribe to this call's events, then collect 4 digits.
con:setEventLock("true")
con:myevents()
con:execute("play_and_get_digits",
            "4 4 3 5000 # ivr/ivr-enter_pin.wav ivr/ivr-that_was_an_invalid_entry.wav mypin \\d+",
            uuid)

-- Wait for the application to finish and read what was collected.
local pin
while con:connected() == 1 do
    local e = con:recvEvent()
    if e then
        local name = e:getHeader("Event-Name")
        if name == "CHANNEL_EXECUTE_COMPLETE" then
            if e:getHeader("Application") == "play_and_get_digits" then
                -- the collected digits are now in the channel variable 'mypin';
                -- the value comes back in the command reply's Reply-Text.
                pin = con:sendRecv("getvar mypin"):getHeader("Reply-Text")
                break
            end
        elseif name == "CHANNEL_HANGUP" then
            break
        end
    end
end

con:execute("hangup", "", uuid)
```

`myevents` 订阅让 `recvEvent()` 循环真正具有意义：连接会变成该通道的事件流，使处理程序能够根据 `CHANNEL_EXECUTE_COMPLETE`、`DTMF` 和 `CHANNEL_HANGUP` 作出反应，而不是盲目调用应用。收集到的按键会写入 `play_and_get_digits` 参数指定的通道变量（此处为 `mypin`），之后可通过 `getvar` 或后续通道快照读取。

:::note
这里的 `con:myevents()` 相当于 `con:sendRecv("myevents")`——即发送原始 `myevents` 命令并读取其 `+OK` 应答。ESL 对象 API 的 `events()` 用于一般事件订阅；出站模式要订阅单通道事件，应使用 `myevents`，并可通过 `sendRecv` 原样发送此命令。
:::

## 何时选择出站或入站模式 {#when-to-use-outbound-vs-inbound}

| 适合使用**出站**模式的情况 | 适合使用**入站**模式的情况 |
| --- | --- |
| 控制单个呼叫（IVR、语音机器人、呼叫筛选），希望每通呼叫对应一条绑定连接。 | 需要跨整个系统监控、记录日志或发起呼叫。 |
| 希望 FreeSWITCH 主动连接应用服务器，并通过 `\|` 分隔多个备用地址实现故障转移。 | 应用是长时间运行的客户端，连接一次后保持在线。 |
| 不希望自行处理身份认证，也不希望根据 UUID 查找呼叫。 | 需要全局 API（`api` / `bgapi`）、全系统事件流，或主动发起新呼叫。 |
| 每次呼叫的控制逻辑短暂且相互独立。 | 一个进程需要同时查看和操作多条通道。 |

两种模式并不互斥。常见架构同时使用入站连接进行全局监控和发起呼叫，再通过 `socket` 应用将特定呼叫交给专门的出站处理程序，实现更细粒度的呼叫控制。
